The platform

Four parts. One way of working.

Each part does one job, and they share the same products, workspaces and evidence.

X4 Code

The developer app. Run Claude and Codex threads across every repository in a product, with the workspace, sandbox and preview controls beside the conversation.

  • Agent threads
  • Product workspaces
  • Previews

X4 Control

The operations workspace. One sign-in for the machines, the model accounts and the product catalogue everything else reads from.

  • FleetServers and devboxes
  • GatewayModel accounts and usage
  • ProjectsProducts and previews
  • DocsGuides and reference

Mastra Factory

Turns Linear issues into agent sessions. Factory plans the work, asks when it is unsure, implements on a devbox and opens the pull request.

  • Linear issues
  • Plans
  • Sessions on devboxes

X4 CLI

The engine underneath. It sets up workspaces, starts previews, runs validation on remote workers and posts results to GitHub. People, editors and agents call the same commands.

$ x4 workspace bootstrap --repo-set storefront

How it works

From issue to evidence.

The same four steps for every product, whether a person or an agent does the work.

  1. 01

    Describe the product

    Register its repositories, environments and preview profiles once in Control. Everyone starts from the same definition.

  2. 02

    Work in a workspace

    X4 Code and Factory open the product’s repositories together on a devbox, on matching branches with the product’s tooling.

  3. 03

    Preview the change

    Start the product at that exact version with the environment you choose, and share it on a private address.

  4. 04

    Review the evidence

    Tests, logs and preview links come from real runs and are attached to the pull request, ready for a person to judge.

Concepts

A small vocabulary.

Three words carry most of X4. They mean the same thing in the docs, in Control and in X4 Code.

productProduct
A named application or service built from one or more repositories. It owns its development and testing environments.
environmentEnvironment
A named set of configuration values and secret references for one product, such as development or testing.
previewPreview
A running instance of a product or repository at a particular version, configured with an environment.

Built-in guardrails

Safe by default.

  • Plans before actionsGitHub and remote commands show what they will do and run only when asked.
  • Private previewsPreview links stay inside the private network. Local-only addresses are refused.
  • Secrets stay secretEnvironments check that keys exist without printing their values.
  • Visible cleanupWorktree, branch and sandbox cleanup is shown before it is applied.
